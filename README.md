# Суммаризатор тендерной документации

Сервис на FastAPI: принимает PDF с сайта госзакупок и возвращает структурированную выжимку - сумма контракта, сроки, требования к исполнителю, штрафы.

Тестовое задание №1.

## Что здесь по существу

Задача выглядит как «отправь PDF в LLM и верни ответ», но в таком виде она разваливается на реальных файлах закупок. Три проблемы, вокруг которых построено решение:

1. **Документация не влезает в окно модели.** Аукционная документация это 50-300 страниц: извещение, ТЗ, проект контракта, приложения. Отправлять всё нельзя, обрезать по первым N символам бессмысленно: раздел про неустойку почти всегда в конце.
2. **Модель уверенно выдумывает суммы и сроки.** Ответ без возможности проверки в тендерах бесполезен: ошибка в НМЦК или в размере обеспечения стоит денег.
3. **JSON от модели не всегда валиден по схеме,** даже в json-режиме.

Ответы: отбор страниц по доменным маркерам, обязательная цитата-подтверждение для каждого значения, одна попытка починки по ошибке валидации.

## Алгоритм

```
PDF (multipart)
  │
  ├─ 1. Приём: чтение кусками по 1 МБ с лимитом, проверка сигнатуры %PDF
  │      мусор и файлы-переростки отсекаются до расхода токенов
  │
  ├─ 2. Извлечение: pypdf постранично, нормализация (переносы, \xa0, пробелы)
  │      суммарно < 200 символов → 422: скан без текстового слоя, нужен OCR
  │
  ├─ 3. Отбор страниц под бюджет символов (app/pdf.py):
  │      • страницы 1-2 берём всегда - там предмет закупки и НМЦК
  │      • остальные ранжируем по числу доменных маркеров:
  │        «начальная (максимальная) цена», «НМЦК», «срок выполнения»,
  │        «требования к участник», «штраф», «пени», «неустойк», ...
  │      • добираем, пока укладываемся в CHAR_BUDGET
  │      • восстанавливаем порядок по номеру страницы
  │
  ├─ 4. Склейка с маркерами «=== Страница N ===»
  │      по ним модель проставляет номер страницы в цитате
  │
  ├─ 5. Вызов LLM: temperature=0, response_format=json_object,
  │      JSON Schema прямо в системном промпте
  │      невалидный ответ → отдаём модели её же ошибку валидации, один ретрай
  │
  └─ 6. Ответ: summary + meta (сколько страниц всего, какие ушли в модель,
         сколько символов, какая модель, сколько заняло)
```

`meta.pages_used` нужен не для красоты: по нему видно, что именно прочитала модель, и почему в ответе нет, скажем, гарантийного срока.

## Формат ответа

Каждое значение снабжено `evidence`: дословная цитата и номер страницы. Не нашлось - `null` или пустой список плюс явная запись в `unresolved`, чтобы «модель не нашла» не выглядело как «в документе этого нет».

```json
{
  "summary": {
    "contract_sum": {
      "amount": 2450000.0,
      "currency": "RUB",
      "vat": "включая НДС 20%",
      "evidence": {"page": 1, "quote": "НМЦК: 2 450 000,00 рублей, включая НДС 20%"}
    },
    "deadlines": [
      {"stage": "выполнение работ", "value": "90 календарных дней",
       "evidence": {"page": 4, "quote": "Срок выполнения работ: 90 календарных дней"}}
    ],
    "requirements": [
      {"text": "Опыт аналогичных работ за 3 года на сумму не менее 50% НМЦК",
       "category": "опыт", "evidence": {"page": 3, "quote": "..."}}
    ],
    "penalties": [
      {"reason": "просрочка исполнения обязательства",
       "amount": "1/300 ключевой ставки Банка России от цены контракта за день",
       "evidence": {"page": 5, "quote": "..."}}
    ],
    "unresolved": ["размер обеспечения гарантийных обязательств"]
  },
  "meta": {
    "pages_total": 5, "pages_used": [1, 2, 3, 4, 5],
    "chars_sent": 2841, "model": "qwen2.5:7b-instruct", "elapsed_ms": 4120
  }
}
```

Штрафы в контрактах почти всегда формула, а не число, поэтому `amount` строка: «1/300 ключевой ставки за каждый день просрочки» нельзя свернуть в float, не потеряв смысл.

## Запуск

Docker (поднимает сервис и локальную модель, платные ключи не нужны):

```bash
docker compose up -d
docker compose exec ollama ollama pull qwen2.5:7b-instruct
curl -F "file=@tests/fixtures/sample_tender.pdf" http://localhost:8000/v1/summarize
```

Локально:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env        # правим LLM_BASE_URL / LLM_API_KEY / LLM_MODEL
uvicorn app.main:app --reload
```

Провайдер любой OpenAI-совместимый: OpenAI, Ollama, vLLM, облачный прокси. Меняется тремя переменными окружения, кода это не касается - поэтому в `app/llm.py` один клиент, а не три адаптера.

Документация API: `http://localhost:8000/docs`.

## Тесты

```bash
pytest -q     # 15 тестов, сеть и ключи не нужны
```

Покрыто то, что ломается на практике:

- извлечение кириллицы из PDF, битый файл, скан без текстового слоя;
- отбор страниц: при нехватке бюджета раздел с неустойкой важнее середины документа;
- соблюдение бюджета символов;
- починка невалидного JSON со второй попытки (ровно одна, не бесконечный цикл);
- ошибка апстрима отдаётся как 502, а не как 500 с трейсбеком;
- мусорный файл отклоняется **до** вызова модели.

LLM в тестах подменяется через `app.dependency_overrides`, транспорт httpx - через `MockTransport`. CI (GitHub Actions): ruff, black, pytest на каждый push и PR.

## Границы решения

Осознанно не сделано, потому что задание про выжимку, а не про платформу:

| Не сделано | Когда добавлять |
|---|---|
| OCR для сканов | как только в потоке появятся сканы: tesseract или облачный OCR перед шагом 2 |
| Постраничный map-reduce | если понадобится гарантия «прочитан весь документ», а не только релевантные страницы |
| Кэш по хешу файла | при повторных загрузках одних и тех же документов |
| Очередь и фоновые задачи | когда время ответа модели начнёт упираться в таймаут HTTP |
| Аутентификация | при выносе наружу; сейчас сервис внутренний |

Отбор страниц по ключевым словам это сознательно простая эвристика: она дешёвая, объяснимая и её видно в `meta.pages_used`. Если на реальном потоке документов она начнёт промахиваться, следующий шаг не «усложнить веса», а прогнать оба варианта на размеченной выборке и сравнить.
